# AGENTS.md — auto-electricity-report-service

Инструкции для coding-агентов. Документ регулирует **процесс разработки**, а не заменяет требования продукта или архитектуру.

## Источники истины

- `docs/PRD.md` — согласованные требования к MVP: пользовательские сценарии, `FR-01`–`FR-17`, `NFR-01`–`NFR-07` и 17 проверяемых сценариев приёмки.
- `docs/ARCHITECTURE.md` — утверждённые технические решения, границы компонентов, хранение данных, генерация документов и сборка Windows-приложения.
- GitHub issues **#1–#6** — конкретные этапы реализации: каркас/БД, расчёты, PDF, GUI, ZIP, проверка и сборка. Содержимое issue определяет объём соответствующей задачи.
- `README.md` — сведения о фактически реализованном состоянии проекта и командах, **когда они будут добавлены**.
- Эталоны акта и счёта, упомянутые в PRD (`.docx` и `.xls`), — источники для проверки **оформления** документов. Не считай их доступными, пока не обнаружил сами файлы или не получил их от пользователя.

**Приоритет:** согласованный PRD определяет поведение продукта, архитектура — способ реализации без противоречия PRD, issue уточняет объём работы, существующий код показывает фактическое состояние. При обнаружении противоречий сообщи о них, не меняй требования молча. Читай относящиеся к задаче разделы, а не пересказывай документы целиком.

**Текущее состояние:** на момент добавления этого файла в репозитории есть `README.md`, `docs/PRD.md`, `docs/ARCHITECTURE.md` и `.gitignore`; приложения, тестов и настроенной системы сборки ещё нет. Дерево в архитектуре — **целевая, а не уже существующая** структура. Перед каждой работой заново проверяй состояние репозитория; не делай выводов по этому историческому описанию.

## Границы MVP

- Это **полностью локальное однопользовательское приложение для Windows 10/11**, без сервера, интернета, облака, аккаунтов, логина, веб-интерфейса и удалённого API.
- Пользователь получает обычную Windows-программу: для работы не нужны установленный Python, терминал или ручная установка зависимостей.
- Один исполнитель; справочник арендаторов первоначально пуст; один счётчик на арендатора; один общий тариф на календарный месяц; возможно несколько независимых расчётов одного арендатора за месяц.
- **Не расширяй MVP без отдельной задачи:** многопользовательский режим, бухгалтерия, контроль платежей, интеграции, квартальные документы, тарифные зоны, несколько счётчиков, редактор шаблонов, постоянный архив PDF и сложное резервное копирование не предусмотрены.
- Изменяй только необходимое для текущего issue. Не добавляй зависимости, инфраструктуру или рефакторинг «заодно».
- **Не коммить реальные реквизиты, данные арендаторов, номера счетов, подписи, печати и пользовательские БД.** Для тестов используй вымышленные сведения. Сборка не должна содержать пользовательских данных.

## Принятый стек и разделение ответственности

- **Python 3**; GUI — **PySide6 / Qt Widgets**; локальная БД — **SQLite** через стандартный `sqlite3`.
- Точная арифметика — **`decimal.Decimal`**, а не `float`. PDF — **ReportLab**, ZIP — стандартный `zipfile`.
- Сборка на Windows — **PyInstaller**, первоначально `onedir`. Не заменяй стек по собственной инициативе.
- Не вводи SQLAlchemy, Alembic, FastAPI/Django, отдельный сервер БД, DI-контейнеры, событийную шину или универсальные репозитории без согласования.

Ориентир из `docs/ARCHITECTURE.md`, **создаваемый постепенно**:

- `app/ui/` — формы, таблицы и диалоги. UI отображает готовность и ошибки, но не определяет бизнес-правила.
- `app/core/calculations.py` — расчёт расхода, суммы и округления; `app/core/validation.py` — проверки и готовность; `app/core/numbering.py` — номера документов.
- `app/data/database.py` — схема, транзакции и SQL. **Не выполняй SQL внутри обработчиков кнопок**.
- `app/documents/` — генерация акта, счёта, PDF/ZIP. Генераторы получают подготовленные данные: **без SQL и скрытого изменения расчётов**.
- `assets/` — неизменяемые ресурсы и необходимые шрифты; `tests/` — тесты. Не создавай пустые слои и файлы ради соблюдения рисунка структуры.

Данные пользователя хранятся **отдельно от исполняемого файла**, например в `%LOCALAPPDATA%/ElectricityReports/`: SQLite и необязательные изображения подписи/печати. PDF/ZIP сохраняются по выбору пользователя, а не в постоянный внутренний архив. Обновление приложения не должно стирать данные.

## Доменная терминология и именование

Используй понятия PRD: **исполнитель**, **арендатор**, **тариф**, **показания**, **расчёт**, **акт**, **счёт**. Для кода придерживайся терминов архитектуры: `tenant`, `tariff`, `reading`, `calculation`, `document`, `act`, `invoice`; не называй один объект разными именами без причины.

- Идентификаторы, имена файлов/веток, сообщения коммитов и заголовки PR — **на английском**. Тексты интерфейса, сообщения ошибок, отчёты агента и описания PR — **на русском**.
- Python: файлы, модули, функции и переменные — `snake_case`; классы — `PascalCase`; константы — `UPPER_SNAKE_CASE`. Соблюдай сложившийся стиль и настройки линтеров, когда они появятся.
- Функции называй по **действию и объекту**: `get_tenant`, `list_calculations`, `create_document`, `calculate_total`, `validate_calculation`. Имя должно описывать результат, а не способ реализации.
- `get_*` — одна сущность, `list_*` — коллекция, `create_*` — создание, `update_*` — изменение, `delete_*` — удаление; `is_*`/`has_*`/`can_*` — булевы проверки; `validate_*` — валидация; `require_*` — обеспечение условия с ошибкой. Избегай расплывчатого `check_*`.
- Обработчики Qt называй содержательно (`handle_save`, `handle_export`); бизнес-правила не прячь в слотах. Не переименовывай существующие публичные интерфейсы только ради стиля.
- Имена тестов описывают **условие и ожидаемое поведение**, например `test_changing_readings_resets_manual_amount` или `test_bulk_export_skips_latest_ready_zero_consumption`.

## Неизменяемые правила расчётов и данных

При затрагивании соответствующих частей сверяйся с полным текстом PRD/архитектуры. Особенно важно:

- **Точность:** показания — до 3 знаков после запятой; тариф — до 4; сумма — до 2 с обычным математическим округлением. Не округляй тариф преждевременно. Для SQLite храни дробные значения без потери точности, например десятичными строками.
- **Формула:** расход = конечные − начальные показания; сумма = расход × тариф месяца. Ручной расход/сумма допускаются после предупреждения. Изменение показаний сбрасывает ручной расход и сумму; изменение расхода или тарифа сбрасывает ручную сумму.
- **Валидация:** конечные показания меньше начальных — черновик сохраняется, PDF блокируется даже при ручном расходе; отрицательная сумма запрещена; при отсутствии тарифа показания сохраняются, а документы недоступны. Нулевой расход: индивидуальная выгрузка — после подтверждения, массовая — пропуск.
- **Период:** расчёт находится внутри **одного календарного месяца**, допускается неполный месяц и несколько расчётов одного арендатора с пересекающимися датами. Перед совпадающим расчётом предупреждай, но не запрещай его.
- **Автоподстановка:** исходные показания берутся из прошлого месяца согласно PRD; ручные сохраняются и не становятся автоматическим источником для аналогичных пропусков без соответствующей настройки. Для сортировки «последний» учитывай `updated_at` и детерминированный ID.
- **Документы:** акт и счёт имеют независимую нумерацию **по году даты документа**; новый номер — максимум существующих для типа/года + 1. Дубликаты допустимы после предупреждения; повторная выгрузка сохраняет номер и дату. Не начисляй НДС; в акте сохраняй формулировку **«Сумма НДС: 0,00»**.
- **Актуальность:** при изменении расчёта/тарифа/реквизитов ранее сформированные логические документы требуют обновления. PDF создаётся по запросу из текущих данных, но не хранится в БД. Не отмечай успешную генерацию, если запись файла завершилась ошибкой.
- **Массовая выгрузка:** для каждого **активного** арендатора выбери последний **готовый** расчёт месяца. Если он нулевой — пропусти, не возвращаясь к более раннему ненулевому. ZIP содержит отдельную папку на арендатора; имена безопасны и уникальны для Windows. Ошибка одного документа не срывает остальные.
- **SQLite:** внешние ключи (`PRAGMA foreign_keys = ON`), транзакции, версия схемы (`PRAGMA user_version`) и простые последовательные миграции. Уникальность `tariffs(year, month)` и `documents(calculation_id, type)` обязательна; **не** запрещай пересекающиеся расчёты или ручные дубли номеров документов.

## Git: коммиты, ветки и PR

**Названия — не разрешение на операции.** Без отдельного поручения не создавай ветки, коммиты и PR, не выполняй push, merge, force-push, `git reset --hard` или деплой. Прямое поручение внести изменение в репозиторий даёт право на необходимую для этого запись, но не на дополнительные Git-операции или merge.

- Сообщения коммитов — **Conventional Commits**: `type(scope): imperative action`, например `feat(core): implement decimal calculations (#2)` или `docs: add agent instructions`.
- Типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `ci`. Scope — предметная часть (`core`, `db`, `documents`, `ui`, `export`, `build`), только когда полезен.
- Если требуется ветка и её создание разрешено: `type/issue-number-short-description`, например `feat/2-decimal-calculations`; без issue — `docs/agent-instructions`. Используй короткое `kebab-case`-описание.
- В проекте задачи обозначены **обычными номерами GitHub issues #1–#6**, а не `TASK-XXX`. Не выдумывай идентификаторы `TASK-*` или `REQ-*`: для связи с требованиями применяй реальные `FR-*`/`NFR-*`.
- PR создавай/изменяй только по прямому поручению. Базовая ветка по умолчанию — `main`; merge — только отдельно. **Заголовок PR на английском**, например `#2 — Implement calculation rules`; без issue — содержательное короткое название.

Описание PR всегда **на русском**, кратко и проверяемо по diff:

1. **Резюме** — результат, связанный issue (`Closes #N` при полном закрытии, иначе `Refs #N`) и соответствующие `FR-*`/`NFR-*`.
2. **Основные изменения** — существенные изменения и их назначение.
3. **Проверки** — фактически выполненные тесты, ручные сценарии и результаты; явно отмечай недоступные проверки.
4. **Ограничения и дальнейшие действия** — известные риски, ручная настройка, недоделки.
5. **Исправления по ревью** — если они были, один блок с идентификаторами замечаний и статусами исправлений.

Обновляй PR после существенных исправлений; создание PR само по себе не означает приёмку.

## Выполнение задачи

1. Прочитай **фактическое** содержимое issue (если оно есть), релевантные `FR-*`/`NFR-*` и связанные сценарии приёмки. Не придумывай требования по одному номеру.
2. Проверь зависимости, текущее состояние кода и границы задачи. Issues #1–#6 задают поэтапную работу, но не разрешают автоматически реализовать следующие этапы.
3. Для нетривиальной задачи коротко обозначь план. При конфликте спецификаций или отсутствии критически важного эталона сообщи об ограничении, не подменяй его выдуманным.
4. Реализуй минимальное законченное изменение в согласованной архитектуре. Не создавай фиктивную готовность функциональности только потому, что она описана в PRD.
5. Добавь или обнови тесты для затронутых правил. Пользуйся **реально существующими** командами проекта. Пока тестовый раннер не настроен, не утверждай, что он уже есть.
6. Запусти доступные проверки, изучи итоговый diff и сообщи о непроверенном. После значимых изменений поддерживай актуальность `README.md` (возможности, зависимости, запуск, тесты, сборка).

## Проверки и безопасность данных

- Особое внимание тестам на **`Decimal`/округление**, ручные корректировки, незаданный тариф, отрицательный и нулевой расход, неполный месяц, пересекающиеся расчёты, нумерацию по дате документа, повторную выгрузку, выбор последнего готового расчёта и частичные ошибки ZIP.
- Проверяй не только правильный результат, но и **сохранность данных** при невалидном вводе, сбое записи, закрытии/повторном запуске и редактировании старых показаний. Зависимые более поздние расчёты не меняй без согласия пользователя.
- Изменения в БД выполняй атомарно; не используй совместное SQLite-соединение из разных Qt-потоков без корректного управления. Не стирай существующую пользовательскую базу ради повторной инициализации или тестов.
- Перед сдачей приложения нужны ручные проверки GUI, визуальное сравнение **обоих** PDF с доступными эталонами, корректность кириллицы, длинных названий и суммы прописью.
- Сборку `onedir` создавай на Windows; проверяй на Windows 10/11 **без Python и интернета**, первый запуск, сохранение после перезапуска и безопасность обновления. Не объявляй эти проверки выполненными, если не проводил.
- Не трогай чужие незакоммиченные изменения. Не выполняй разрушительные действия с БД, файлами или Git без прямого разрешения.

## Завершение задачи

Отчитайся **на русском**:

- **Задача:** номер issue (если есть), статус и относящиеся `FR-*`/`NFR-*`.
- **Изменения:** что сделано и какие файлы затронуты.
- **Проверки:** точные команды/сценарии, результаты и то, что проверить не удалось.
- **Ограничения:** известные риски, расхождения с эталонами, открытые вопросы и оставшаяся работа.

Работа готова **к приёмке**, когда выполнены критерии соответствующей задачи, соблюдены PRD и архитектура, проведены доступные проверки и нет посторонних изменений. **Окончательно принимает результат пользователь.**
