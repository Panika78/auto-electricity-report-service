# auto-electricity-report-service

Настольное офлайн-приложение «Контакт» для учёта электроэнергии и подготовки актов и счетов.

## Реализовано в issue #1

- Запуск минимального окна на **PySide6 / Qt Widgets** и сообщение об ошибке инициализации базы.
- Создание SQLite-базы с таблицами `tenants`, `tariffs`, `calculations`, `documents`, `settings`.
- Транзакции, внешние ключи, миграции через `PRAGMA user_version`. При повторном запуске проверяется целостность и полнота схемы: повреждённая база не перезаписывается и приводит к явной ошибке.
- Функции создания, чтения, просмотра списка и обновления сущностей в `app/data/database.py`.
- Сохранение базы **вне приложения**, при повторном запуске записи не сбрасываются.

Нативные экраны PySide6, индивидуальный экспорт PDF и бизнес-логика реализованы в issues #2–#4; массовая ZIP-выгрузка — в #5. Для issue #6 предусмотрены сценарий сборки Windows и автоматическая проверка собранного EXE. Полная приёмка на чистых Windows 10/11 проводится отдельно.

## Windows x64 — сборка и передача MVP (Issue #6)

**Статус:** подготовка релизного кандидата; автоматическая проверка на Windows Server 2022 не заменяет приёмку на чистых **Windows 10 и Windows 11 x64**. См. [журнал 17 сценариев](docs/RELEASE_ACCEPTANCE.md).

### Для пользователя (без Python, интернета и прав администратора)

1. Получить проверенный файл `kontakt-windows-x64.zip` от разработчика. Не использовать архив `Source code` из GitHub как готовую программу.
2. Распаковать ZIP в обычную папку, например `Документы\Программы\контакт\`. **Не запускать EXE прямо внутри ZIP.**
3. Открыть `kontakt\kontakt.exe` двойным щелчком. Все файлы папки `kontakt`, включая `_internal`, должны оставаться вместе; терминал и установка Python не нужны.
4. Для обновления **полностью закрыть** программу, сохранить резервную копию пользовательских данных, затем заменить только папку программы новой распакованной папкой `kontakt`. Не удалять и не заменять папку данных из пункта ниже. Запустить новый `kontakt.exe` и проверить арендаторов, документы, подпись и печать.

**Хранение данных:** SQLite: `%LOCALAPPDATA%\ElectricityReports\app.db`; новые импортированные подписи/печати: `%LOCALAPPDATA%\ElectricityReports\images\` (при работе с явно указанной БД изображения лежат **рядом с этой БД**). PDF и ZIP сохраняются в выбранную пользователем папку, не внутри дистрибутива. Настройки размера/жирности шрифта хранятся в пользовательских настройках Qt (`QSettings`) и не требуют прав администратора. Обновление программы **не** сбрасывает SQLite или эти настройки. У старых установок картинки могли оказаться в отдельном каталоге Qt: существующие абсолютные пути в SQLite продолжают работать; **не удаляйте старые изображения**, пока они используются.

**Резервная копия:** закрыть приложение, скопировать весь каталог `%LOCALAPPDATA%\ElectricityReports\` в безопасное место (включая `images`). Не отправлять этот каталог вместе с ZIP дистрибутива и не публиковать его в GitHub. Если экспорт или запуск завершился ошибкой, не удалять и не переименовывать реальную БД наугад.

### Для сборки (Windows x64, Python 3.11 x64)

В **чистом checkout** запустить в PowerShell 7 из корня репозитория:

```powershell
./scripts/build_windows.ps1
```

Скрипт создаёт отдельное `.venv-release`, устанавливает закреплённые версии из `requirements-windows-build.txt`, запускает все тесты с `QT_QPA_PLATFORM=offscreen`, создаёт `onedir` через `kontakt.spec` и проводит запуск **реального собранного EXE** в отдельном синтетическом профиле. Папка дистрибутива: `dist/kontakt/`; итоговый ZIP: `dist/kontakt-windows-x64.zip`; перечень фактических Python-зависимостей: `dist/build-requirements.txt`. Хэш SHA-256 выводится в конце сборки и сохраняется в **`dist/release-manifest.json`** вместе с `build_checkout_commit` (фактический коммит checkout), `build_tree_sha` (Git-дерево исходников) и `pr_head_commit` (отдельный HEAD PR, если применимо). Сборка прекращается при незакоммиченных изменениях, включая неотслеживаемые файлы. Сверяйте именно `zip_sha256` для *внутреннего* `kontakt-windows-x64.zip`; не используйте хэш ZIP-обёртки GitHub Actions. Скрипт **не удаляет** существующую `.venv-release`: используйте чистую рабочую копию для повторяемой сборки. Отсутствующие колёса, плагины Qt или шрифты приводят к ошибке, а не к «успешной» сборке.

Альтернатива: GitHub Actions → **Windows onedir release candidate** → Run workflow, или запуск сборки для PR в `main`. Скачать артефакт `kontakt-windows-x64-rc` (внутри ZIP поставки, `release-manifest.json` и `build-requirements.txt`). Для проверки целостности используйте `python scripts/check_release_manifest.py --manifest dist/release-manifest.json --zip dist/kontakt-windows-x64.zip --build-checkout-commit <SHA-фактического-checkout> --build-tree-sha <SHA-дерева>` либо `Get-FileHash` и значение `zip_sha256` из манифеста. Workflow работает на **Windows Server 2022**, где есть Python для сборки и тестов: это не доказательство совместимости с Windows 10/11 без Python. Исполняемый файл в тесте вызывается с ограниченным `PATH`, но это не эквивалент чистой ОС; отключение интернета также требует отдельной ручной проверки.

Для релизной проверки скрипт дважды запускает `kontakt.exe --release-smoke` с обязательными переменными `KONTAKT_RELEASE_SMOKE`, `KONTAKT_SMOKE_ROOT`, `KONTAKT_SMOKE_TOKEN`, `KONTAKT_SMOKE_RESULT`. Режим требует маркер и одноразовый случайный токен, создаваемые инструментом внутри **нового пустого временного профиля**. Настоящий Windows-профиль определяется через Shell API независимо от переменной `LOCALAPPDATA`; совпадения двух переменных окружения недостаточно. Без действительного маркера тестовая БД и настройки не открываются. Проверяются загрузка Qt, сохранение SQLite, импорт изображения, генерация реальных PDF/ZIP и повторный запуск после замены папки бинарников. Отдельно собранный EXE запускается **без** `--release-smoke` через Qt `windows` и проверяется наличие видимого нативного окна с последующим закрытием. Для тестового профиля `QSettings` принудительно использует локальный INI и не обращается к настоящим настройкам HKCU. Этот тест всё равно не заменяет ручные действия с реальным GUI. Проверки отказа доступа к папке экспорта, повреждённой базы, визуального совпадения с эталонами и живой работы GUI на Windows 10/11 выполняются вручную по `docs/RELEASE_ACCEPTANCE.md`.

Скрипт `scripts/validate_windows_bundle.py` проверяет список ресурсов по разрешённым типам и каталогам, а также соответствие содержимого итогового ZIP проверенной папке сборки. Отдельные негативные автотесты гарантируют отклонение посторонних `bank-details.txt`, `clients.csv` и `private-scan.png`. Эта проверка не является исследованием содержания каждого бинарного файла и требует сборки из доверенного чистого репозитория.

**Ограничения воспроизводимости:** основные версии зависимостей закреплены; полный набор разрешённых косвенных зависимостей сохраняется через `pip freeze`, но сборка не заявляется побитово идентичной между разными образами Windows/днями сборки. Не подменяйте результаты ручной приёмки зелёным CI.

## Где хранятся данные

На Windows: `%LOCALAPPDATA%\ElectricityReports\app.db`.

Для разработки на Linux/macOS: `$XDG_DATA_HOME/ElectricityReports/app.db` либо `~/.local/share/ElectricityReports/app.db`.

Невалидные относительные системные пути (`LOCALAPPDATA`, `XDG_DATA_HOME`) приводят к ошибке, а не к записи рядом с программой. База не хранится в каталоге исходников или рядом с исполняемым файлом. Путь к тестовой БД задаётся явно через `Database(path)`; пользовательская БД в тестах не используется.

## Работа со слоем данных

Используйте `Database` и отдельные функции `create_tenant`, `get_tenant`, `list_tenants`, `update_tenant` и аналогичные для тарифов, расчётов и документов. Настройки исполнителя представлены одной записью (`get_settings`, `update_settings`); она создаётся при миграции. Десятичные значения передаются строками или `decimal.Decimal`, при чтении возвращаются как `Decimal`. `float` для показаний/сумм не допускается.

```python
from decimal import Decimal
from tempfile import TemporaryDirectory
from pathlib import Path
from app.data.database import Database, create_tenant, get_tenant

with TemporaryDirectory() as directory:
    db = Database(Path(directory) / "app.db")
    db.initialize()
    with db.transaction() as conn:
        tenant_id = create_tenant(conn, name="Тестовый арендатор", initial_reading=Decimal("0.125"))
    with db.connection() as conn:
        print(get_tenant(conn, tenant_id))
```

Все операции записи выполняются внутри `with db.transaction() as conn:`; при ошибке изменения этой транзакции откатываются. Чтение — в `with db.connection() as conn:`. SQL находится только в модуле `app.data.database`.

## Реализовано в issue #2: бизнес-логика

- Независимые от GUI расчёты `Decimal`: до 3 знаков показаний/расхода, 4 у тарифа, 2 у суммы с `ROUND_HALF_UP`, сумма прописью.
- Готовность к документам допускает денежную сумму **строго меньше 10^18 рублей** (максимум 999 999 999 999 999 999,99 ₽), которую поддерживает функция перевода суммы прописью; бо́льшие суммы сохраняются как неготовые расчёты.
- `CalculationService` в `app/core/service.py`: создание и автосохранение черновиков, начальные показания, пересекающиеся/неполные периоды, ручные корректировки, пересчёт тарифов, проверка готовности и массовый выбор.
- `ConfirmationRequired` с `code` и `affected_ids` возвращается до записи при пересечении, исправлении истории, ручной корректировке, изменении использованного тарифа, удалении, дублирующемся номере или нулевой выгрузке. После подтверждения вызов повторяется с соответствующим `confirm_*`.
- Документы: `next_document_number`, `reserve_document`, `prepare_document`, `document_status`. Только **после успешного сохранения PDF** генератор должен вызвать `mark_document_generated(document_id, expected_revision=snapshot["revision"])`; при ошибке записи PDF этот метод не вызывается. Сами PDF в этом issue не формируются.
- Все операции записи сервиса выполняются в транзакциях `Database.transaction()`; низкоуровневые функции `app.data.database` предназначены для слоя данных. GUI должен использовать именно сервис, иначе можно обойти проверки и отметку актуальности.
- Автоподстановка ручного начала без конечного показания допускается лишь при включённой настройке и явном `confirm_manual_reuse=True`.

- Изменение тарифа пересчитывает значения и помечает документы устаревшими, но **не меняет `updated_at` расчётов**, чтобы не менять порядок выбора источника/массовой выгрузки.
- После `confirm_history=True` изменённые автоматически унаследованные (`start_reading_source='previous_month'`) начала последующих месяцев согласуются с предыдущим месяцем, расход/сумма пересчитываются, документы помечаются для обновления. Ручные начала не заменяются. При удалении единственного источника унаследованное начало очищается и остаётся привязанным к прошлому месяцу для возможной синхронизации в будущем.
- При создании нового завершённого расчёта задним числом с последующими записями сервис запрашивает `confirm_history=True`, а при согласии синхронизирует автоматические начала и документы в одной транзакции. При переносе расчёта в другой месяц сервис отдельно пересчитывает автоматически унаследованное начало **самого перенесённого расчёта** по новому предыдущему месяцу; ручное начало сохраняется.
- Для первичных показаний используйте `CalculationService.create_tenant` / `update_tenant` (отрицательные значения и `float` запрещены).
- `bulk_candidates()` возвращает `skipped` со структурированным `reason` (`no_calculation`, `missing_tariff`, `incomplete_readings`, `invalid_readings`, `not_ready`, `zero_consumption`); для неготового расчёта также возвращается `errors` валидатора.
- **Политика для незавершённых расчётов (FR-06/FR-07, уточнена в PRD в этом PR):** пропускаем записи предыдущего месяца без конечного показания и используем последнюю заполненную по `updated_at DESC, id DESC`. Сам Issue #2 это правило не детализирует. Если заполненных записей нет — ручное начало или явно подтверждённое резервное; в более ранние месяцы не заглядываем.
- `prepare_document()` возвращает `revision` со снимком значений расчёта: при `mark_document_generated()` проверяется и снимок данных, и времена правок; не переиспользуйте снимок после исправления истории.


Пример программного интерфейса:

```python
from decimal import Decimal
from pathlib import Path
from tempfile import TemporaryDirectory
from app.core.service import CalculationService
from app.data.database import Database, create_tenant

with TemporaryDirectory() as directory:
    database = Database(Path(directory) / "demo.db")
    database.initialize()
    with database.transaction() as conn:

```

## PDF-документы (Issue #3)

Подсистема `app.documents` формирует акт и счёт на оплату через ReportLab. Макеты различаются и воспроизводят структуру исходных Word/Excel-документов; реальные эталоны, реквизиты и изображения не хранятся в репозитории.

```python
from app.documents import export_document, export_documents, safe_filename

# service = CalculationService(database), calculation_id — существующий готовый расчёт.
result = export_document(service, calculation_id, "act", "act.pdf", confirm_zero=False)
# Для двух документов передайте словарь путей:
results = export_documents(service, calculation_id, {"act": "act.pdf", "invoice": "invoice.pdf"})
# Перезапись существующего PDF — только с overwrite=True.
```

При необходимости пользователь подтверждает нулевой расход через `confirm_zero=True`, а дубликат номера — через `confirm_duplicate=True`. Номер и дату можно установить через `number=` и `document_date=` в `export_document`. Отмена до начала сохранения — `cancelled=True`. `ExportBatchResult.successful` и `failed` отражают результат каждого документа независимо.

Генераторы `render_act(snapshot)` и `render_invoice(snapshot)` не обращаются к SQLite или Qt, не пересчитывают суммы и возвращают байты PDF. Сервис резервирует номер и создаёт согласованный снимок данных, а статус «сформирован» устанавливает только после успешного сохранения файла и проверки ревизии. При сбое обновления статуса экспорт пытается восстановить предыдущий файл; в исключении `ExportError.recovery_failed` фиксируется ситуация, когда восстановление не удалось. Полной транзакционности между файловой системой и SQLite нет.

Кириллические PT Serif/PT Sans шрифты лицензированы по SIL OFL 1.1 и находятся в `app/documents/fonts/`, чтобы входить в wheel и будущую Windows-сборку без системных шрифтов. Пользовательские изображения подписи/печати остаются в пользовательском хранилище и не включаются в пакет. В PyInstaller-сборке необходимо сохранить директорию `app/documents/fonts` как package data.

Проверка: `python -m pip install -e ".[test]"`, затем `QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -v`. Диалоги выбора пути и подтверждений относятся к #4, ZIP — к #5.

### Устойчивость экспорта после ревью PR #11

При `overwrite=True` после неудачного восстановления файл резервной копии сохраняется, а `ExportError.backup_path` указывает на него; `recovery_error` и исходная ошибка (`__cause__`) доступны отдельно. После успешного сохранения и отметки SQLite ошибка удаления резервной копии не превращает экспорт в неуспешный: `ExportedDocument.cleanup_warning` и `leftover_backup` сообщают о необходимости ручной очистки конфиденциального временного файла. На файловых системах без hard links используется эксклюзивное создание и безопасное удаление неполной записи при сбое; при ошибке удаления сообщаются `ExportError.path` и `cleanup_error`. Выбор нескольких PDF требует разных физических путей; проверяются также файловые алиасы и регистронезависимые каталоги. Полная гарантия на фоне вмешательства другого процесса или внезапного отключения питания невозможна, поскольку SQLite и файловая система не имеют общей транзакции.

Спорное правило нулевой суммы при ненулевом расходе **не менялось**; сценарии и предложение по согласованию приведены в `docs/PDF_LAYOUT.md`.

### Диагностика оставшихся файлов (R-08/R-09)

При неудачном откате прежний PDF не перезаписывается, если невозможно проверить идентификатор текущего файла. `ExportError.backup_path` хранит путь к прежнему документу, `ExportError.quarantine_path` — к файлу, сохранённому при защищённом откате. `ExportError.staged_path` и `partial_path` указывают на временный/частично записанный файл, если автоматическая очистка не удалась. Ошибки очистки доступны в `cleanup_error` и `cleanup_errors`, первичная ошибка — в `__cause__`. Для успешной публикации очистка не меняет статус: `ExportedDocument.cleanup_warning`, `leftover_staged` и `leftover_backup` доступны интерфейсу для ручной очистки приватных файлов. Не выводите реквизиты из самих PDF в логи.
  
### Оформление PDF (F-01–F-04, F-06)

Оба генератора (`render_act`, `render_invoice`) используют общую типографику **PT Sans** и одинаковые поля A4, сохраняя индивидуальную структуру Word-акта и Excel-счёта. Для энергии в обоих документах используется `кВт·ч`. Дробные показатели выводятся с десятичной запятой и разделением тысяч пробелами, без потери точности; суммы — с двумя дробными разрядами. Прежняя шапка счёта с условиями продажи/отпуска товаров удалена. Эти изменения не затрагивают расчёты и статусы SQLite. Изображения и конфиденциальные образцы остаются вне репозитория. Одна позиция в документе соответствует одному расчёту; произвольные дополнительные позиции текущая модель не предусматривает.


## Нативный интерфейс «контакт» (Issue #4)

Запуск после установки зависимостей: `python -m app.main`. Интерфейс использует Qt Widgets, а не HTML-прототип:

- **Расчёты:** старт с предыдущего месяца, смена периода, реальный KPI-обзор, тариф, все расчёты месяца, поиск и фильтры. При открытии и изменении размера окна таблица **автоматически подгоняет ширину столбцов**; при ручном перетаскивании границ размер фиксируется до нажатия **«Сбросить и подогнать»**. Длинные числа сохраняют читаемость с помощью локальной горизонтальной прокрутки; длинные названия переносятся. Расчёт открывается двойным щелчком или кнопкой, изменения существующих полей автосохраняются после завершения ввода.
- **Арендаторы:** карточное представление, создание, редактирование реквизитов и договора, исходные показания, история. **Архив открывается кнопкой в разделе «Арендаторы»** (отдельного пункта в левом меню нет); восстановление подтверждается.
- **Настройки:** реквизиты единого исполнителя, подпись и печать (изображения копируются в локальное хранилище). Во вкладке **«Оформление»** два независимых ползунка: размер текста **80–200% с шагом 5%** (по умолчанию 100%) и насыщенность **300–800 с шагом 100** (по умолчанию 400). Значения после перетаскивания мышью **округляются к ближайшему шагу**: 103% → 105%, вес 450 → 500. Подписи, предпросмотр и положение ползунков отражают выбранное значение. Доступны отдельные и общий сбросы; сохранение через Qt `QSettings` не влияет на PDF, SQLite и статусы документов.
- **PDF:** в карточке расчёта или из таблицы выберите акт/счёт, номер и дату, путь для каждого PDF. После подтверждения совпадения номера, нулевого расхода или перезаписи (при необходимости) экспорт выполняет `app.documents.export_document`; интерфейс не помечает документ сформированным самостоятельно.

**Ввод показаний:** в диалоге последовательно расположены арендатор и даты, начальные/конечные показания, **два независимых чекбокса** «Изменить расход вручную» и «Изменить сумму вручную», затем блок **«Предварительный расчёт»**. При включении чекбокса можно ввести ручное число непосредственно в поле под ним; изменение подтверждается. Снятие чекбокса возвращает формульный расчёт. При одновременном изменении ручных значений сначала сохраняется расход, затем сумма. Предпросмотр показывает расход, тариф, сумму, готовность и причины ошибок ещё **до сохранения**. Начальное показание может подставляться автоматически из предыдущего расчёта или карточки арендатора и остаётся автоматическим до явной ручной правки.

**Даты периода:** календарь позволяет выбирать **только дни текущего расчётного месяца**. Например, для ноября 2026 — с 01.11.2026 по 30.11.2026; внутри него можно указать неполный период. Попытка обойти ограничение программно блокируется также при сохранении с указанием выбранного месяца.

Создание нового арендатора или расчёта подтверждается кнопкой «Создать». После создания допустимые изменения отдельных полей сохраняются автоматически. Неполные показания остаются черновиками, ошибки показываются в карточке. Если сохранение не удалось, при закрытии диалога пользователь получает предупреждение о несохранённых изменениях.

**Согласованные правила UI:** [docs/UI_UX.md](docs/UI_UX.md). [HTML-прототип](docs/kontakt-prototype.html) — визуальный ориентир, но некоторые его элементы намеренно отличаются от более поздних решений: старые переключатели шрифта заменены на слайдеры, пункт архива убран из левой панели, информационные блоки удалены. Бизнес-требования определяет [PRD](docs/PRD.md).

Автоматизированные проверки: `QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -v`. Регрессии в `tests/test_gui_workflows.py` проверяют в том числе шаги ползунков и перетаскивание мышью, повторное открытие настроек, ограничения календарей, неполный месяц и ручные корректировки. Используются временные SQLite-базы и синтетические реквизиты. **Offscreen-тесты не заменяют ручной визуальный осмотр на Windows**.


## Массовая ZIP-выгрузка (Issue #5)

На странице «Расчёты» кнопка «Выгрузить всех · ZIP» сохраняет акты и/или счета активных арендаторов за выбранный месяц. Используется последний готовый расчёт; нулевой расход и неготовые расчёты пропускаются с пояснением. Документы каждого арендатора помещаются в собственную папку внутри ZIP; имена безопасны и однозначны даже при совпадающих названиях и номерах. Проверяются конечные компоненты пути по правилам Windows, включая зарезервированные имена `COM¹`–`COM³`, `LPT¹`–`LPT³` и варианты с расширением; недопустимые имена ZIP отклоняются до резервирования документов. Пустой ZIP не создаётся.

ZIP собирается во временном файле и публикуется перед единым транзакционным обновлением статусов. Если архив сохранён, но фиксация SQLite не удалась, ZIP остаётся, а предупреждение прямо говорит, что статусы не подтверждены. При отсутствии hard links новый ZIP публикуется атомарным переименованием **без замены** (Windows: `os.rename`; Linux: `renameat2(RENAME_NOREPLACE)`). Если файловая система не поддерживает ни один безопасный способ, экспорт прекращается без создания частичного ZIP по конечному пути. Копирование непосредственно в конечный путь запрещено. Существующий ZIP заменяется только после подтверждения и подготовки нового содержимого. Если опубликованный ZIP изменён или удалён до проверки целостности, результат не считается успешно выгруженным и интерфейс показывает отдельную ошибку содержимого (не путать со сбоем фиксации SQLite). Перед обновлением статусов повторно проверяется, что выбранный расчёт всё ещё последний готовый у арендатора.

Проверка: `QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests -v`; `python -m compileall -q app tests`.
