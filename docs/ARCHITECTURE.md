# Архитектура приложения для учёта электроэнергии

**Проект:** auto-electricity-report-service  
**Версия:** 1.0  
**Дата:** 12.11.2026  
**Статус:** согласованное архитектурное решение для MVP  
**Основание:** [PRD](./PRD.md)

## 1. Цель и принципы

Продукт — небольшая офлайн-программа для одного человека (порядка 14 арендаторов), а не промышленная бухгалтерская система. Архитектура должна помогать быстро добавлять функции, исправлять ошибки и доставлять работающее Windows-приложение.

Принципы:

1. **Один процесс и один компьютер.** Без сервера, API, облака, авторизации и сетевой инфраструктуры.
2. **Запуск без Python у пользователя.** Разработчик использует Python, но заказчик получает готовую сборку для Windows 10/11.
3. **Простая структура.** Отделить интерфейс, правила расчёта, сохранение данных и генерацию документов; не вводить формальные слои ради слоёв.
4. **Единый источник правды.** Расчёты и метаданные документов хранятся локально; PDF формируются по запросу.
5. **Исправления — обычный сценарий.** Пользователь может менять расчёты и повторно выгружать документы без ручного восстановления связанных данных.
6. **Локальная устойчивость.** Автосохранение завершённых изменений, атомарные изменения в БД, проверка данных перед генерацией.

## 2. Выбранные технологии

| Задача | Выбор | Обоснование |
| --- | --- | --- |
| Язык | Python 3 | Небольшой объём прикладной логики, простое тестирование |
| GUI | PySide6 / Qt Widgets | Настольный интерфейс: таблицы, формы, диалоги |
| База данных | SQLite + стандартный \`sqlite3\` | Один локальный файл, без сервера и ORM |
| Расчёт денег | \`decimal.Decimal\` | Отсутствие ошибок двоичного \`float\` в тарифах и суммах |
| PDF | ReportLab | Точный контроль расположения реквизитов и изображений |
| ZIP | \`zipfile\` | Стандартная библиотека |
| Сборка Windows | PyInstaller (\`onedir\` на первом этапе) | Самостоятельный exe с включёнными зависимостями |
| Проверки | \`unittest\` или \`pytest\` | Тесты расчётов, нумерации и правил выбора документов |

**Осознанно не используем:** SQLAlchemy, FastAPI/Django, отдельную БД-сервер, микросервисы, DI-контейнеры, универсальный движок шаблонов и сложные фреймворки состояний.

Использование Python во время разработки **не означает** требование установки Python на компьютере заказчика.

## 3. Общая схема

\`\`\`text
[Пользователь]
      |
      v
[PySide6: главное окно, формы, настройки]
      |
      v
[Прикладные операции / правила]
      |                     |
      v                     v
[SQLite через sqlite3]  [ReportLab: акт и счёт]
                            |
                            v
                      [PDF / ZIP файлы]
\`\`\`

Это **монолитное десктопное приложение**, а не взаимодействие между отдельными сервисами. Интерфейс вызывает понятные прикладные функции; те обращаются к БД и генератору документов. Правила расчётов не зависят от Qt и могут тестироваться отдельно.

## 4. Структура репозитория

Предлагаемая целевая структура (не обязательно создавать все файлы до появления соответствующей логики):

\`\`\`text
auto-electricity-report-service/
├── app/
│   ├── main.py                 # Точка входа и инициализация
│   ├── ui/
│   │   ├── main_window.py      # Таблица за выбранный месяц
│   │   ├── tenant_dialog.py    # Карточка арендатора

│   ├── core/
│   │   ├── calculations.py     # Decimal, расход, сумма, округление
│   │   ├── validation.py       # Готовность расчёта и предупреждения
│   │   └── numbering.py        # Номера актов и счетов
│   ├── data/

│       ├── invoice.py          # PDF счёта
│       └── export.py           # Выгрузка PDF/ZIP, безопасные имена
├── assets/                     # Шрифты и неизменяемые ресурсы, если нужны

Не обязательно добавлять отдельные абстракции \`Repository\`, \`Service\` и \`Controller\` для каждой таблицы. На MVP достаточно явных функций с понятными входными и выходными значениями. **SQL не пишется внутри обработчиков кнопок** — он локализован в \`data/database.py\`.

## 5. Данные и их размещение

### 5.1. Локальные файлы

Пример каталога данных пользователя Windows:

\`\`\`text
%LOCALAPPDATA%/ElectricityReports/
├── app.db                  # SQLite: все структурированные данные
└── images/
    ├── signature.png       # Необязательно
    └── stamp.png           # Необязательно
\`\`\`

- Каталог программы/сборки и **пользовательские данные должны быть разделены**: переустановка или обновление \`.exe\` не должны удалять расчёты.
- Подпись и печать не вшиваются в исполняемый файл и могут отсутствовать.
- PDF/ZIP сохраняются в место, выбранное пользователем через стандартный диалог Windows, и **не копируются в постоянное внутреннее хранилище**.
- Отдельный UI резервного копирования для MVP не обязателен. БД должна оставаться доступной для обычного резервного копирования файла при закрытом приложении.

### 5.2. Минимальная схема SQLite

| Таблица | Что хранит |
| --- | --- |
| \`tenants\` | ID, название, реквизиты, договор/допсоглашение, архивный статус, исходные показания и дату |
| \`tariffs\` | Год, месяц, единый тариф для месяца |
| \`calculations\` | ID, tenant_id, год/месяц, начальная/конечная дата, показания, расход, сумма, признаки ручных корректировок, готовность, created_at, updated_at |
| \`documents\` | ID, calculation_id, тип (\`act\`/\`invoice\`), номер, дата документа, метка актуальности и информация о последней генерации |
| \`settings\` | Реквизиты единого исполнителя, пользовательские настройки, пути изображений (либо относительные ссылки) |

Допустимы вспомогательные поля и таблицы, если они действительно нужны при реализации, но исходная модель остаётся небольшой.

Обязательные правила:
- У каждого арендатора постоянный внутренний **ID** — название и договор могут меняться.
- У каждого расчёта собственный **ID**; на одного арендатора в одном месяце могут приходиться несколько расчётов с пересекающимися датами. Уникальное ограничение по периоду **не вводить**.
- Таблица \`tariffs\` имеет уникальную пару \`(year, month)\`.
- В \`documents\` хранится не более одной записи каждого типа на один расчёт: уникальная пара \`(calculation_id, type)\`.
- **Номер документа не уникален**: PRD допускает дубли после предупреждения. Не вводить \`UNIQUE(type, year, number)\`.
- Год нумерации определяется **датой документа**, а не месяцем расчёта.
- Денежные и дробные величины хранить **без \`float\`**: например, как десятичные строки \`TEXT\`, переводя в \`Decimal\` при расчёте. Точность: показания до 3 знаков, тариф до 4, сумма — 2.
- Использовать внешние ключи и транзакции; включить \`PRAGMA foreign_keys = ON\` для соединения. Логика удаления расчёта должна корректно удалить метаданные его документов.
- Для выбора «последнего созданного/изменённого» использовать \`updated_at\` с детерминированным разрешением равенств через ID; одинаковые даты и одинаковые показания не запрещаются.

**Нюанс о начальных показаниях из пропущенного месяца:** ручное значение автосохраняется в текущем расчёте, но по умолчанию не становится автоматически переиспользуемой заменой отсутствующих исторических показаний в других расчётах. Такое переиспользование включается настройкой; для этого достаточно сохранять признак происхождения начального показания.

**Схема БД** меняется по мере разработки. Для локальных обновлений достаточно простого номера версии структуры (например, \`PRAGMA user_version\`) и последовательных небольших SQL-миграций — без Alembic.

## 6. Правила взаимодействия компонентов

### 6.1. Расчёт

\`\`\`text
expense_kwh = end_reading - start_reading
total_rub = round_to_kopecks(expense_kwh * month_tariff)
\`\`\`

- Вся арифметика — \`Decimal\`, округление суммы до копеек; не округлять тариф до 2 знаков раньше времени.
- При изменении показаний сбросить ручную корректировку расхода, пересчитать расход и сумму.
- При изменении показаний, расхода или тарифа сбросить ручную корректировку суммы.
- Если конечное показание меньше начального, **сохранить черновик**, но заблокировать генерацию даже при ручном расходе.
- Если тариф не задан, сохранять показания, но не выдавать документы.
- При ручной корректировке расхода или суммы предупреждать, не требовать пояснения для акта.
- При изменении тарифа, который уже использовался, запрашивать подтверждение массового перерасчёта.

### 6.2. Автосохранение

- Интерфейс передаёт изменения одной записи через функции сохранения в БД.
- Невалидные промежуточные значения в поле (например, пока пользователь набирает число) не должны приводить к ошибкам БД: сохранять после допустимого изменения/завершения редактирования; незавершённый расчёт может иметь статус «Не готов».
- Каждое логически цельное изменение сохранять в одной транзакции. Сообщать о неудачном сохранении, не показывать ложный успех.
- После сохранения обновлять строку таблицы и статусы. Данные других арендаторов не трогать.
- Если изменение исторических показаний затрагивает более поздние расчёты, до их изменения показать пользователю затронутые записи и получить подтверждение.

### 6.3. Готовность и статусы

Вся бизнес-проверка сосредоточена в \`core/validation.py\`; UI только отображает результат.

Отдельно учитывать:
- **Готовность расчёта:** есть корректные показания, допустимый диапазон внутри одного месяца, неотрицательный расход, установлен тариф, корректная сумма.
- **Состояние каждого документа:** ещё не создавался / сформирован / требует обновления.
- **Режим выгрузки:** нулевой расход допускается индивидуально после подтверждения; в ZIP пропускается.

Для отметки «Требует обновления» при изменении расчёта, тарифов или реквизитов можно явно помечать связанные записи \`documents\` как неактуальные. Альтернативно — сравнивать ревизии источников; **для MVP выбрать один простой механизм**, не дублируя оба.

### 6.4. Генерация и нумерация

- При **первом создании** документа присвоить номер по правилу \`MAX(существующих номеров данного типа за год даты документа) + 1\`; при пустом наборе — 1. Номер и дата сохраняются в \`documents\`.
- У актов и счетов независимые серии; при новом году последовательности начинаются с 1.
- Пользователь может вручную поменять номер или дату; повтор номера вызывает предупреждение, но допустим.
- Если документ уже создан, повторное скачивание **сохраняет** номер и дату.
- Удаление расчёта удаляет и связанные записи документов; освободившийся максимальный номер снова доступен автоматически, прочие пропуски — только вручную.
- Генератор получает **подготовленные данные документа**, не выполняет SQL-запросы и не изменяет расчёты.
- В PDF показываются текущие реквизиты и актуальные расчётные значения, но сохранённые номер и дата документа.
- ReportLab генерирует документы максимально близкие к эталонам Word и Excel; обязательно учесть шрифты с кириллицей, перенос длинных названий, суммы прописью и необязательные картинки подписи/печати.
- Документы не сохраняются в БД: можно повторно создать актуальный PDF по запросу.

**Порядок безопасной выгрузки:** сначала проверить данные и подготовить PDF во временном файле/буфере; затем фиксировать необходимые метаданные и завершать сохранение по выбранному пути. Если выгрузка не удалась, показать ошибку и не отмечать документ как успешно сформированный. Конкретную обработку сбоев файловой системы реализовать так, чтобы пользователь мог безопасно повторить операцию.

### 6.5. Массовая выгрузка

Псевдокод выбора:

\`\`\`text
для каждого активного арендатора:
    получить расчёты выбранного месяца от новых к старым
    выбрать первый готовый расчёт
    если нет: пропустить с причиной
    иначе если расход == 0: пропустить с причиной
    иначе: сформировать выбранные виды документов
собрать успешные PDF в ZIP
показать список успехов и пропусков
\`\`\`

- Не выбирать предыдущий ненулевой расчёт, если **последний готовый** имеет расход 0.
- Не поддерживать произвольный выбор подгруппы арендаторов: только все или один.
- Ошибка генерации одного документа не должна прерывать остальные; результат должен объяснять, что именно не удалось.
- ZIP организовать по папкам арендаторов; файловые имена делать уникальными и безопасными для Windows, даже при одинаковых номерах.
- Для обычного масштаба (около 14 организаций) не требуется отдельная очередь задач; если создание ZIP заметно блокирует окно — выполнить экспорт в рабочем потоке Qt, передав ему подготовленные данные, а не разделяемое соединение SQLite.

## 7. Интерфейс

**Три основные области:**

1. **Главный экран.** Месяц (по умолчанию предыдущий), таблица арендаторов и расчётов, показания, расход, сумма, статус акта/счёта, поиск, фильтры, индивидуальная и массовая выгрузка.
2. **Арендаторы.** Добавление/редактирование, архивирование/восстановление, договоры, первоначальные показания, переход к истории.
3. **Настройки.** Реквизиты исполнителя, подпись/печать, опция переиспользования вручную введённых начальных показаний.

Другие сценарии — небольшие диалоги: создание второго расчёта за месяц, редактирование сумм, подтверждение исправлений/удалений, предупреждение о дублирующемся номере и выбор PDF/ZIP.

Принцип: показать пользователю **что он меняет, что пересчитается и почему документ нельзя скачать**. Не скрывать ошибки за общим сообщением «что-то пошло не так».

## 8. Сборка, распространение и проверка

1. Разрабатывать и тестировать на обычном Python-окружении.
2. Собирать приложение **на Windows** через PyInstaller; на первом этапе формат \`onedir\` (папка с \`.exe\` и зависимостями), а не обязательно один физический файл.
3. Включать необходимые шрифты и неизменяемые ресурсы в сборку.
4. Не включать пользовательскую БД или реальные подписи в дистрибутив.
5. На тестовой Windows 10 и Windows 11 проверить работу **без установленного Python** и без интернета, первый запуск, сохранение после перезапуска, корректность PDF/ZIP и отсутствие потери данных при обновлении приложения.
6. При необходимости позже упаковать папку приложения в обычный Windows-установщик с ярлыком. Система автообновлений не нужна.

## 9. Тесты, которые особенно важны

Автоматические тесты для:
- расчёта с дробными показаниями и тарифами до четырёх знаков;
- округления в \`Decimal\` и суммы прописью;
- сброса ручных корректировок после изменения исходных данных;
- нулевого и отрицательного расхода;
- отсутствующего тарифа;
- года по **дате документа**, независимых серий актов/счетов, ручного номера, удаления максимального номера;
- нескольких расчётов с совпадающим периодом;
- выбора последнего **готового** расчёта для ZIP и пропуска нулевого;
- повторной генерации с прежними номером и датой;
- сохранения данных после закрытия и повторного открытия;
- отказа одного документа без повреждения других.

Небольшое количество ручных проверок GUI и визуальное сравнение PDF с двумя предоставленными образцами обязательны перед передачей заказчику.

## 10. Что не усложняем заранее

- Нет отдельной сети, REST API, микросервисов и синхронизации.
- Нет ORM, универсального слоя репозиториев, контейнеров зависимостей и событийной шины.
- Нет системы контроля версий документов и постоянного архива PDF.
- Нет сложных фоновых заданий, кроме возможного неблокирующего экспорта ZIP.
- Нет специальных бизнес-сценариев, которых нет в PRD.

**Критерий хорошей реализации:** заказчик может открыть приложение, ввести показания, скачать документы и легко исправить ошибку. Сложность внутреннего устройства не должна становиться сложностью для пользователя.
