## Правила отчётности

- `PASS`: проверка выполнена, ожидаемый результат подтверждён. В строках Windows 10/11 и PRD источник подтверждения — **владелец приложения, 16.11.2026**, не независимый CI-протокол.
- `FAIL`: проверка действительно выполнена, наблюдалось несоответствие.
- `BLOCKED`: нет достоверного результата для полного критерия, например отсутствует чистая Windows 10/11, приватный эталон или ручная GUI-проверка.
- Запуск unit-тестов и offscreen-тестов PySide6 **не равен** ручной приёмке готового `.exe`.
- Не переносить подтверждения из автотестов на разные Windows без реального запуска; при сомнении `BLOCKED`.

## Ответ на замечания ревью PR #14

- **R-03:** релизный манифест создаётся **после** архивации; содержит фактический checkout SHA, SHA дерева исходников, отдельный HEAD PR, имя и SHA-256 поставляемого ZIP. CI сверяет значения раздельно. Статический хэш предыдущего прогона оставлен только как историческое свидетельство, не как текущая контрольная сумма.
- **R-04:** помимо обычного `--release-smoke` добавлен отдельный запуск собранного EXE **без ключей** через `qwindows.dll`: обнаружение видимого Win32-окна по PID/заголовку, штатное закрытие и проверка отдельной БД. Это проверяет лишь путь открытия и закрытия нативного GUI; реальные действия, диалоги и визуальная вёрстка остаются ручными.
- **R-05:** в контролируемом QA-режиме настройки Qt сохраняются в отдельный INI внутри временного профиля, с проверкой сохранения при повторном запуске. Обычные пользовательские настройки Windows в HKCU не меняются.
- **R-06:** импорт и удаление управляемых изображений используют `service.database.path.parent / "images"`. Для двух независимых тестовых баз проверяются отсутствие пересечений и запрет удаления чужого изображения.
- **R-07:** проверка состава включает разрешённые пути PDF-шрифтов/лицензий, Qt runtime-библиотек и ресурсов; лишние текстовые файлы и пользовательские изображения не проходят. Проверяется и состав готового ZIP. Остаётся ограничение: содержимое бинарных DLL не анализируется семантически, поэтому нужен доверенный чистый checkout.
- **R-08:** маркер QA с криптографически случайным токеном создаётся только для нового пустого временного профиля; Windows Shell API независимо от `LOCALAPPDATA` блокирует реальные системные каталоги. Без маркера тестовая БД не открывается.
- **R-09:** формат манифеста 2 отдельно хранит `pr_head_commit`, `build_checkout_commit` и `build_tree_sha`. Локальная сборка с dirty/untracked файлами отклоняется.
- **R-10:** результат QA допускается исключительно внутри профиля, разрешённого маркером и токеном, под уникальным именем `qa-result-<32 hex>.txt`. После проверки пути запись выполняется только через эксклюзивное создание, без перезаписи. При ошибке авторизации никакой отчёт не создаётся, даже если `KONTAKT_SMOKE_RESULT` указывает на посторонний файл. Есть негативные тесты для существующего файла внутри и вне профиля.
- **R-11:** workflow после успешной загрузки ZIP обновляет специальный блок описания PR: HEAD, реальный checkout, Git-дерево, URL **того же** run, ID загруженного артефакта, хэш внутреннего ZIP из проверенного манифеста. Перед записью и после неё проверяется актуальность PR и значения; устаревший workflow не должен перезаписывать новую ссылку. Эта автоматизация разрешена лишь для PR внутри того же репозитория.
- **R-01 и R-02:** владелец 16.11.2026 сообщил, что провёл ручные испытания на Windows 10/11 и проверил все 17 сценариев. Это отражено статусом `PASS`, а не независимой проверкой; версии ОС, SHA использованного ZIP и подробные протоколы не предоставлены.
- **Оригинальная иконка:** используются только файлы владельца `app/assets/kontakt-icon.ico` (Windows EXE и Qt) и `app/assets/kontakt-icon.svg`. Проверяются неизменность исходных байтов и соответствие ресурсам сборки; smoke-тест проверяет Qt-иконку.

### Ручной протокол (только на синтетическом профиле)

1. Взять ZIP из GitHub Actions, проверить целостность SHA-256, распаковать на **отдельном** тестовом аккаунте Windows 10 x64, затем повторить на Windows 11 x64; на обеих машинах без Python, с отключённым интернетом и без повышения привилегий.
2. Проверить начальный экран и все 17 сценариев таблицы через реальный интерфейс, обязательно открывая получившиеся PDF и ZIP.
3. Добавить синтетические реквизиты, историю, начисления, подпись/печать и настройки шрифта; закрыть EXE, заменить ТОЛЬКО папку `kontakt` другой сборкой и перепроверить данные в `%LOCALAPPDATA%\ElectricityReports`.
4. Для отказа записи выбрать **заведомо недоступную** тестовую директорию и проверить, что документ не помечен успешным. Для повреждения базы создать отдельный тестовый профиль с повреждённым `app.db`; проверить отказ без удаления или сброса. **Не изменять реальную БД заказчика.**
5. Сравнить акт и счёт с переданными локально эталонами, включая кириллицу, шрифты, табличную сетку, сумму прописью, подпись и печать. Ни PDF с реальными реквизитами, ни образцы не коммитить.
6. Записать версии Windows (например, по `winver`), разрядность, дату, SHA-256 ZIP, наблюдаемые результаты и найденные дефекты. Только после этого менять `BLOCKED` на `PASS` или `FAIL`.
