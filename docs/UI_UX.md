# UI/UX-спецификация «контакт» — согласованный HTML-прототип

**Дата согласования:** 14.11.2026  
**Статус:** согласовано для дизайна прототипа (пользовательская приёмка)  
**Прототип:** [kontakt-prototype.html](./kontakt-prototype.html)  
**Проверка покрытия:** [KONTAKT_PROTOTYPE_REVIEW.md](./KONTAKT_PROTOTYPE_REVIEW.md)

## 1. Область действия и приоритет

Этот документ фиксирует **принятые решения об интерфейсе**, которых не было в деталях в [PRD](./PRD.md) и [архитектуре](./ARCHITECTURE.md). Он дополняет их, но не меняет бизнес-правила. Приоритет источников: PRD → архитектура → задача (issue) в её пределах → эта спецификация визуального решения. При расхождении поведения с PRD необходимо следовать PRD и отдельно согласовать исправление прототипа.

Поставляемый конечному пользователю продукт остаётся **локальным Windows-приложением на PySide6 / Qt Widgets** с SQLite и ReportLab. HTML — исключительно автономный интерактивный прототип, а не смена архитектурного стека или веб-версия MVP.

## 2. Визуальная система

- Название бренда пишется **«контакт»**, строчными буквами.
- В фирменном написании часть **«акт» выделяется цветом** относительно «конт», где логотип/wordmark уместен. Не нужно раскрашивать любое употребление слова в обычном тексте.
- Фирменная пиктограмма — **молния, не волна**.
- Одобренное визуальное направление: тёплый нейтральный фон (ориентир `#f6f4ef`), светлые поверхности (`#fffefa`), тёмная стальная боковая панель (`#192a2f`), терракотовый основной акцент (`#c55e3c`). На тёмной панели для «акт» применяется более светлый оттенок (`#ec946d`), чтобы сохранять читаемость.
- Дизайн: минималистичные таблицы и карточки, выраженная иерархия, понятные статусы, видимый keyboard focus, адаптивное расположение; данные в таблицах могут горизонтально прокручиваться на небольших экранах. Конкретные пиксельные размеры HTML не навязываются Qt.

## 3. Навигация и экраны

Основные функциональные области из архитектуры §7 остаются прежними:

1. **Расчёты:** месяц по умолчанию — предыдущий; тариф, показания, расход, сумма, статусы акта и счёта; поиск/фильтры; создание и исправление расчёта; индивидуальный PDF и массовый ZIP.
2. **Арендаторы:** создание/изменение, договор и реквизиты, первоначальные показания, история, архивирование.
3. **Настройки:** исполнитель и реквизиты, изображения подписи и печати, переиспользование ручных начальных показаний, управление типографикой.

**Архив арендаторов должен быть явно доступен:** отдельный пункт «Архив» в навигации, а также переход из справочника арендаторов. В архиве можно открыть карточку и историю, восстановить арендатора по подтверждению. Архивный арендатор не включается в массовую выгрузку. Архив — представление уже предусмотренного PRD FR-02 статуса, не отдельный новый тип сущности.

Расчёты за несколько периодов и несколько расчётов одного арендатора за месяц не должны становиться недоступными из-за упрощённой навигации.

## 4. Управление типографикой

В разделе **Настройки → Оформление** пользователь может независимо изменить:

| Параметр | Значения | Поведение |
| --- | --- | --- |
| Размер шрифта | Меньше / Обычный / Крупнее | Мгновенно применяется к интерфейсу |
| Насыщенность шрифта | Лёгкий / Обычный / Жирный | Мгновенно применяется к интерфейсу |

Выбранные параметры сохраняются при повторном открытии приложения в рамках доступного ему локального хранилища. Значения по умолчанию — обычный размер и обычная насыщенность. Элементы переключения должны сообщать активное значение и быть доступны с клавиатуры. Изменение этих настроек **не является редактированием расчётов** и не помечает акт/счёт «Требует обновления»; на содержимое формируемых документов настройка не влияет.

В HTML-прототипе для демонстрации используется `localStorage`; в PySide6 следует использовать соответствующее локальное хранилище настроек без добавления сервера или аккаунтов.

## 5. Требования к поведению и ограничениям прототипа

- Каждый доступный контрол должен совершать осмысленное действие; деструктивные операции и влияющие на другие расчёты изменения требуют предупреждения/подтверждения по PRD.
- Экранные расчёты должны соблюдать десятичную точность; отсутствие тарифа, обратный ход показаний и нулевой расход должны сопровождаться понятными объяснениями.
- Статусы **акта и счёта** независимы; доступ к номеру и дате документа сохраняется при повторной генерации согласно PRD.
- Для демонстрации используются только вымышленные данные. Демо-сброс, браузерное хранилище, генерация PDF и ZIP прямо в JavaScript — **механизмы прототипа**, а не новые продуктовые требования.
- PDF в прототипе условные и не заменяют обязательную сверку актов и счетов с исходными эталонами Word/Excel. Браузер не может надёжно подтвердить успешную запись скачанного файла на диск; статус выгрузки в HTML трактуется как демонстрационная подготовка/запуск загрузки.

## 6. Трассировка

- **PRD FR-02** — архивирование и восстановление арендаторов → отдельная навигация «Архив».
- **PRD FR-16 и NFR-03** — доступность основных действий → основной экран и ясные переходы.
- **PRD FR-17** — изменение старых расчётов и предупреждения → диалоги подтверждения и объяснения.
- **Архитектура §7** — три основных области → общая информационная архитектура.
- **Согласованные дополнительные UI-решения от 14.11.2026** — фирменная молния, цветовое выделение «акт», параметры размера и насыщенности шрифта.

Заданные здесь визуальные решения согласованы по принятому HTML-прототипу; они не означают, что промышленная реализация, пиксельное соответствие Qt и PDF-макеты уже проверены.
